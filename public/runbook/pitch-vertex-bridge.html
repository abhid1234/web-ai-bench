Pitch 3 — LiteRT × Vertex AI: Close the Cloud-to-Edge Gap

TL;DR — "Google's cloud-to-edge gap costs us developers every day"

  • The gap: Google has world-class cloud training (Vertex AI), world-class on-device runtime (LiteRT), and the world's largest mobile platform (Android). None of these talk to each other for custom models. A developer who trains on Vertex today manually performs 6 steps entirely outside Google's product surface before their model runs on Android.
  • The pitch: Build 4 integration points that connect Vertex AI → Firebase → Android/iOS/Web → LiteRT into a single workflow. The target state: a developer clicks "Export to LiteRT" in Vertex Model Garden and 10 minutes later their model is live in their mobile app.
  • The market moment: AWS SageMaker Edge was deprecated in April 2024 — the market's largest cloud-to-edge player exited. Apple has this end-to-end for iOS (Core ML + Xcode + App Store). No Android equivalent exists anywhere. Google can own this market.
  • Partnerships background required: Managing Harness, Datadog, and Lovable at Google Cloud provides direct CI/CD and DevOps ecosystem relationships — not a cold pitch.
  • Duration: 9–12 months. Highest strategic leverage of the three pitches. Start with Kaggle (internal, zero politics) to prove the concept before approaching Vertex and Firebase PMs.

§1. The Problem (Verified)

Three completely disconnected Google products, each with a different PM, different roadmap, different developer experience:

CURRENT STATE — three isolated pipelines, zero connection points for custom models: ┌─────────────────────────────────────┐ │ VERTEX AI │ │ Train, fine-tune, host in cloud │ │ AutoML Edge → TFLite (image only) │ │ Custom models: no edge export path │ └─────────────────────────────────────┘ │ │ ← "Download weights" — developer leaves Google's product surface here ▼ ┌─────────────────────────────────────┐ │ DEVELOPER'S LAPTOP / LOCAL ENV │ │ litert-torch convert (manual) │ │ quantize (manual) │ │ test on device (manual) │ └─────────────────────────────────────┘ │ │ ← still outside Google's product surface ▼ ┌─────────────────────────────────────┐ │ FIREBASE AI LOGIC (rebranded 2025) │ │ Pivoted to Gemini API │ │ TFLite hosting: exists but │ │ undocumented, not connected to │ │ Vertex, not actively developed │ └─────────────────────────────────────┘ │ │ ← separate SDK, separate developer journey ▼ ┌─────────────────────────────────────┐ │ LITERT (Android / iOS / Web) │ │ On-device inference │ │ Completely separate product │ │ No Vertex integration │ │ No Firebase integration │ └─────────────────────────────────────┘
TARGET STATE — one integrated workflow, all within Google's product surface: Vertex AI fine-tune → "Export to LiteRT" button → auto-convert + quantize → Firebase ML hosts model → Firebase SDK → Android/iOS/Web app → LiteRT SDK loads model → inference on device Every arrow = a product surface Google owns. Zero manual steps in a terminal window outside Google products.
The Apple benchmark: Apple Core ML achieves exactly this for iOS — a developer trains in Create ML or any framework, converts to Core ML format, integrates via Xcode, ships through App Store. The pipeline is so seamless that Core ML adoption is strong despite Apple Silicon being a closed ecosystem. LiteRT's runtime is technically superior to Core ML, but Apple's developer workflow is 5× less friction. This pitch closes that gap — and LiteRT covers Android, iOS, and Web, not just one platform.

§3. The Kaggle-First Strategy

Kaggle is Google-owned (Google LLC), has 50M+ registered users, and its model hub is already a training output surface for ML practitioners — many of whom want to deploy to Android or Web. Starting with Kaggle is the right move for 3 reasons:

  1. Zero cross-org politics. Kaggle is Google. No Vertex AI PM or Firebase PM needs to approve the first integration. The Kaggle PM is the single decision-maker.
  2. Proves the concept. A "Deploy to LiteRT" button on Kaggle Models demonstrates that the Vertex integration idea works before Partnerships PM walks into the Vertex AI PM conversation asking for a roadmap commitment.
  3. Large developer reach immediately. Kaggle's 50M users include many who train small CV and NLP models and want them on Android — exactly the LiteRT audience. The button appears in their existing workflow with zero new adoption barrier.
KAGGLE-FIRST PROOF CONCEPT: Developer trains CV model in Kaggle Notebook → Model appears in Kaggle Models hub → "Deploy to LiteRT" button appears on eligible models (eligibility: model outputs are shapes compatible with LiteRT) → Clicks button → Kaggle runs litert convert on backend → Downloads .tflite + auto-generated model card → (Phase 2) pushes to litert-community via litert push This is integration point 4 from the full pitch — but it ships first, in month 2–3, to prove the end-to-end concept before approaching Vertex PM.
Negotiation sequence: Ship Kaggle "Deploy to LiteRT" button (month 2–3) → use Kaggle adoption data in the Vertex PM meeting (month 4) → "Here's what happens when we add this button to Kaggle. The same button in Vertex Model Garden would hit 10× the developer audience."

§4. The Four Integration Points — Detailed Design

Integration Point 1 — Vertex Model Garden "Export to LiteRT"

Current state: Vertex AutoML has a TFLite export option for image classification and object detection — but it is not branded as LiteRT, not surfaced for partner or custom models, and not connected to any Firebase or litert-community workflow. Verified: cloud.google.com/vertex-ai/docs/export/export-edge-model

Target state: Every compatible model in Vertex Model Garden — partner fine-tuned models, Gemma variants, custom training jobs — has an "Export to LiteRT" action that:

MODEL GARDEN UI ADDITION: [Model Card: sentence-transformers/all-MiniLM-L6-v2] ┌────────────────────────────────────────────┐ │ Deploy options: │ │ [Deploy to endpoint] [Export to LiteRT] ←── NEW BUTTON └────────────────────────────────────────────┘ On click → modal: ✓ Auto-convert (runs litert-torch on Vertex backend — no local install) ✓ Choose quantization: FP32 / FP16 / INT8 (with accuracy delta preview) ✓ Benchmark preview: estimated latency on Pixel 8, iPhone 15, Chrome M3 ✓ Output options: → Download .tflite → Push to litert-community (OAuth with HF) → Push to Firebase ML (if Firebase project linked) ✓ Auto-generate model card with benchmark data

Phase delivery:

  • Phase 1 (month 4–5): Backend only — Vertex API accepts .export(format='litert') as a parameter on existing AutoML Edge export. No UI change. Accessible via Python SDK and gcloud CLI.
  • Phase 2 (month 6–8): Model Garden UI button. Quantization modal. Benchmark preview pane.
  • Phase 3 (month 9–12): Vertex custom training jobs — model.export(format='litert') after any custom training job.

Python SDK design (Phase 1 target API):

from google.cloud import aiplatform

# After training or fine-tuning a model on Vertex
model = aiplatform.Model(model_name="projects/.../models/...")

# Export to LiteRT (.tflite) — new in Phase 1
export_job = model.export_model(
    export_format_id="litert",
    artifact_destination="gs://my-bucket/exports/",
    quantization="int8",           # or: "fp16", "none"
    validate=True,                 # run accuracy gate post-conversion
    tolerance=0.02,                # max allowed accuracy drop
)

export_job.wait()
print(export_job.output_info)

Integration Point 2 — Firebase ML + LiteRT Model Hosting

Current state: Firebase AI Logic (rebranded May 2025 from Firebase ML) pivoted to the Gemini API for GenAI use cases. TFLite model hosting still exists and works — but it's undocumented in new Firebase docs, not connected to Vertex, and not actively marketed. Verified: firebase.google.com/products/firebase-ai-logic

What Partnerships PM is NOT asking Firebase to build: A new ML platform. Firebase has pivoted; don't fight it.

What Partnerships PM IS asking Firebase to do: Expose a documented path for LiteRT custom model hosting — essentially a GCS bucket with OTA update semantics — that Vertex can push to directly.

FIREBASE + LITERT INTEGRATION DESIGN: CURRENT (hidden, undocumented): Developer manually uploads .tflite to Firebase Console → FirebaseML.getInstance() .getRemoteModel(customModel) → model available OTA in app TARGET (documented, Vertex-connected): Option A — Vertex-push path: Vertex export_model(format='litert') + firebase_project=my-project → Firebase ML hosts the .tflite automatically → No manual upload, no Firebase Console required → OTA update in app next time user opens app Option B — Manual push path (for developers not on Vertex): litert push model.tflite --hub firebase --project my-firebase-project → Same result as Option A → Works for any .tflite, not just Vertex-trained IN-APP SDK (unchanged — this already works): val model = FirebaseRemoteModel("my-custom-litert-model") val interpreter = LiteRTInterpreter.create(model)

The engineering ask on Firebase's side is minimal: Add a documented API endpoint that accepts a GCS URI from Vertex and registers it in Firebase ML hosting. The hosting infrastructure already exists. This is a plumbing PR, not a new product.

Integration Point 3 — Android Developer Docs + Studio Integration

Current state: Android developer docs (developer.android.com/ai) already recommend LiteRT as the custom inference runtime. But the docs assume developers arrive with a .tflite file — there is no "where do I get a model?" or "how did I train and convert it?" context. The Vertex → LiteRT workflow is completely absent from Android docs.

Target state (3 deliverables, each independent):

  • Official use case pattern in Android docs: A new guide titled "Train on Vertex AI, deploy with LiteRT on Android." This requires a Technical Writer and an Android DevRel — not an Android engineer. The content is: "here's the Vertex Python snippet, here's litert convert, here's the Firebase OTA update, here's the LiteRT Android SDK call." Partnerships PM writes the draft; Android DevRel reviews and publishes. Engineering ask on Android team: 0 hours.
  • Android Studio LiteRT DevKit template: A new Android Studio project template ("On-Device ML with LiteRT") that ships with the litert-bench-action pre-configured in the repo's GitHub Actions workflow. The template is a static project scaffold — it doesn't require Android Studio source code changes, just a new template file contributed to the Android Studio template gallery.
  • Google Play "Verified for On-Device AI" listing badge (stretch goal): A discovery mechanism for apps that use LiteRT + verified model. Not required for Pitch 3 success — flag as a Phase 3 idea for the Android partnership conversation.

Integration Point 4 — Kaggle Models "Deploy to LiteRT" Button

This is the first integration to ship. See §3 for the rationale. Design:

KAGGLE MODELS PAGE — UI CHANGE: Model card for "mobilenet-v3-small-100-224" ┌─────────────────────────────────────────────┐ │ Tasks: Image Classification │ │ Framework: TensorFlow / SavedModel │ │ │ │ [Download] [Open in Colab] [→ LiteRT] ←── NEW BUTTON └─────────────────────────────────────────────┘ On click → side panel: Quantization: [FP32] [FP16] [INT8] Target: [Web] [Android] [iOS] [All] Output: ○ Download .tflite ○ Add to my litert-community collection [Convert and Download] Backend: Kaggle runs litert convert via a Kaggle kernel (same environment as model training — no external API call needed) Conversion result appears as a new "Formats" tab on the model card.

Eligibility logic (which models get the button):

  • TensorFlow SavedModel or Keras .h5 format (direct .tflite conversion path)
  • PyTorch models with litert-torch support (image classification, text embedding, object detection)
  • Model output shape is compatible with known LiteRT task types (auto-detected)
  • Model size < 2GB (practical size limit for web target)

§7. Internal Alignment Strategy

Why this fails without GM support on day 1

Pitch 3 has 4 product team dependencies: Vertex AI, Firebase, Android, Kaggle. Each has their own OKRs. None of them will add a LiteRT integration to their roadmap because Partnerships PM asked nicely. They need a reason — either executive pressure (GM/VP tells them to prioritize it) or a business case compelling enough to move their OKRs. The Kaggle-first strategy (§3) is designed to build the business case before Partnerships PM walks into those rooms. But the room itself needs the GM to open the door.
