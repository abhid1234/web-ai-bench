Pitch 2 — LiteRT DevKit: Edge AI CI/CD Pipeline

TL;DR — "Docker push for edge AI"

  • The gap: Zero GitHub Actions for TFLite/LiteRT exist on the Marketplace today (verified May 2026). Deploying a trained model to Android, iOS, and Web takes 6 manual steps across 3 different tools — all outside Google's product surface. The runtime itself has split (LiteRT for general .tflite, LiteRT-LM for LLMs / RAG / generation), doubling the developer pain. ExecuTorch — now a Linux Foundation / PyTorch Foundation Core project as of April 2026 — shipped a CLI and benchmark dashboard in April 2026. LiteRT has neither.
  • The pitch: LiteRT DevKit — an open-source CLI (pip install litert-devkit) covering both LiteRT and LiteRT-LM, three GitHub Actions, workflow templates for the use cases the team is championing (on-device RAG, translation, camera+LLM, all powered by Gemma 4 E2B/E4B), and a public benchmark dashboard — that collapses 6 manual steps into one pipeline. litert convert && litert push becomes the standard command, the way docker build && docker push became standard a decade ago.
  • Built-in distribution channel: Google × Qualcomm runs LiteRT hackathons. The next confirmed event is in Sunnyvale, April 30 – May 1, 2026; the January 2026 hackathon's BeyondMaps showcase confirmed the format works. DevKit ships as the official tooling — every participant uses litert convert && litert push from day one.
  • What's NOT this pitch: Android 16's AICore system service already serves Gemini Nano centrally for general-purpose AI (~940 tok/s on Pixel NPU, OS-managed memory and battery). DevKit is for the second world: domain-specific custom models — proprietary CV, vertical LLMs, regulated-data inference — that AICore won't host. The two are complementary, not competitive.
  • Partnerships background required: Managing Harness, Datadog, and Lovable at Google Cloud provides direct CI/CD and DevOps ecosystem relationships — not a cold pitch.
  • Launch moment: The 12 @litertjs/core models + 3 HF Spaces + co-authored blog post (formerly "Pitch A") are the DevKit's launch marketing moment — every model was produced by litert convert && litert push. The blog post becomes the DevKit's product launch story.
  • Duration: 6–9 months initiative. Partnerships PM leads product + partnerships. LiteRT eng builds (1–2 engineers, ~80 hrs).

§1. The Problem

A developer who fine-tunes a model on Vertex AI or trains in PyTorch and wants to deploy it to Android, iOS, and Web must perform every step manually today:

CURRENT WORKFLOW (6 manual steps, 3 tools, 0 Google product surface after step 1): Step 1: Export weights from training job → downloads to local disk Step 2: Convert to .tflite → litert-torch convert (standalone CLI, not in any CI system) → or: python -c "import tf; tf.lite.TFLiteConverter..." → no standard command, no error messages that make sense Step 3: Quantize (FP32 → INT8 for performance) → LiteRT Model Optimizer (separate standalone tool) → not wired to CI, no accuracy gate Step 4: Validate accuracy post-quantization → NOTHING EXISTS. Developer eyeballs it or runs custom script. Step 5: Benchmark latency across platforms → Manual: sideload APK, run on physical device, read logcat → No cross-platform comparison, no automated report Step 6: Push to model registry / app → git + S3 / manual HF upload / separate app store deploy → no model versioning, no rollback, no lineage RESULT: A 6-step process that takes 1–3 days per model update, is error-prone, and cannot be run in CI.
The ExecuTorch threat is live. ExecuTorch v1.2.0 (released April 1, 2026) ships with: optimum-cli export executorch model_id --task text-generation — single command PyTorch → ExecuTorch. A public nightly benchmark dashboard at pytorch.org/executorch — automated cross-device perf tracking. Production deployment in Meta's apps: Instagram, WhatsApp, Ray-Ban Smart Glasses, Meta Quest 3. LiteRT's tooling window is 12–18 months before "ExecuTorch has better tooling" becomes entrenched developer perception.
The only existing edge CI/CD competitor is Edge Impulse — which ships edgeimpulse/build-deploy@v1 (GitHub Action) for MCU/embedded .tflite. Small community, MCU-focused, not applicable to Android/iOS/Web. The enterprise CI/CD market (GitHub Actions, Harness, GitLab CI) has exactly 0 LiteRT or TFLite coverage. Verified April 30, 2026.

§3. What LiteRT DevKit Is — Component Design

Component 1 — litert CLI

A single installable command-line tool. Entry point for the entire developer workflow.

pip install litert-devkit        # installs the CLI
litert --version                  # 1.0.0
litert --help                     # lists all commands

Command: litert convert

litert convert <model_path> [flags]

Flags:
  --format          tflite (default), litert-lm
  --quantize        none (default), int8, float16, dynamic
  --target          web, android, ios, all (default: all)
  --output          output file path (default: <model>.tflite)
  --validate        run accuracy validation after conversion (requires --ref)
  --ref             reference model for accuracy comparison
  --tolerance       max allowed accuracy drop (default: 0.02 = 2%)

Examples:
  litert convert model.pt --quantize int8 --validate --ref model.pt
  litert convert model.pt --format tflite --target web --output model_web.tflite

Command: litert validate

litert validate <model.tflite> [flags]

Flags:
  --ref             original model (PyTorch / SavedModel) for numerical comparison
  --dataset         evaluation dataset path (.tfrecord, .csv, directory)
  --metric          accuracy, f1, mse, cosine-sim (auto-detected from model task)
  --tolerance       max allowed metric drop from ref (default: 0.02)
  --output          JSON report path (default: stdout)

Example:
  litert validate model.tflite --ref model.pt --dataset val/ --tolerance 0.01

Output:
  {
    "status": "pass",
    "ref_accuracy": 0.923,
    "tflite_accuracy": 0.918,
    "delta": -0.005,
    "tolerance": 0.01,
    "within_tolerance": true
  }

Command: litert bench

litert bench <model.tflite> [flags]

Flags:
  --targets         web, android, ios, desktop (comma-separated, default: all)
  --backend         webgpu, wasm, gpu-delegate, nnapi, cpu (default: auto)
  --device-farm     browserstack, aws-device-farm, local (default: local)
  --runs            number of inference runs per backend (default: 100)
  --output          json, markdown, html (default: markdown)
  --post-to         github-pr, dashboard (appends to public benchmark dashboard)
  --log-wandb       log results to Weights & Biases run

Example:
  litert bench model.tflite --targets web,android --post-to github-pr

Output (markdown, pasted as PR comment):
  | Backend      | Median latency | P95 latency | Accuracy |
  |------------- |----------------|-------------|----------|
  | WebGPU       | 18ms           | 24ms        | 91.8%    |
  | WASM/XNNPack | 71ms           | 89ms        | 91.8%    |
  | Android GPU  | 12ms           | 19ms        | 91.8%    |
  | Android NPU  | 8ms            | 11ms        | 91.7%    |

Command: litert push

litert push <model.tflite> [flags]

Flags:
  --hub             litert-community (default), mlflow, wandb, gcs
  --repo            HF repo name (e.g. all-MiniLM-L6-v2-web)
  --auto-card       auto-generate model card from bench results + model metadata
  --version         semantic version tag (default: auto-increment)
  --private         private repo (default: public)
  --benchmark-data  path to bench JSON to embed in model card

Example:
  litert push model.tflite --hub litert-community --repo mobilenet-v3-web --auto-card

What auto-card generates:
  - Model card YAML header (license, tags, pipeline_tag, library_name: litert)
  - Benchmark table from most recent litert bench run
  - Usage code snippet (@litertjs/core for web, LiteRT SDK for Android/iOS)
  - Conversion provenance (source model, quantization method, LiteRT version used)

Component 2 — GitHub Actions Suite

Three pre-built, published actions under google-ai-edge/ on the GitHub Marketplace. A developer adds them to their repo in under 10 minutes.

Full workflow example (drop this into .github/workflows/litert.yml):

name: LiteRT CI

on:
  pull_request:
    paths:
      - 'model/**'
      - 'training/**'

jobs:
  litert-pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Step 1: Convert the trained model to .tflite
      - uses: google-ai-edge/litert-convert-action@v1
        with:
          model: model.pt                     # path to source model
          quantize: int8                      # quantization level
          output: model.tflite                # output path
          validate: true                      # run accuracy validation
          tolerance: 0.02                     # max 2% accuracy drop allowed

      # Step 2: Benchmark across platforms (posts results as PR comment)
      - uses: google-ai-edge/litert-bench-action@v1
        with:
          model: model.tflite
          targets: web,android               # which platforms to bench
          device-farm: browserstack          # or: aws-device-farm, local
          post-to: github-pr                 # posts markdown table as PR comment
          post-to-dashboard: true            # opt-in to public benchmark dashboard

      # Step 3: Gate the merge on accuracy + latency thresholds
      - uses: google-ai-edge/litert-gate-action@v1
        with:
          model: model.tflite
          min_accuracy: 0.985               # block if accuracy falls below this
          max_latency_ms_web: 50            # block if WebGPU latency exceeds this
          max_latency_ms_android: 30        # block if Android GPU exceeds this
What this looks like on a PR: The litert-bench-action posts a formatted comment with a benchmark table. The litert-gate-action posts a green checkmark (pass) or red X (fail) with the specific metric that caused the failure. The PR cannot be merged if the gate fails — same pattern as code coverage gates or type check gates.
